# 设计文档 —— 杰理音频容器逆向与转换工具

本文记录从 `音频文件转换工具_1.2.2.exe` 出发，到做出 `wav_tool` 的完整过程。
所有结论都标注 **[已验证]**（可以复现）或 **[推断]**（根据结构推测）。

---

## 1. 原始程序的结构还原

### 1.1 外壳

`音频文件转换工具_1.2.2.exe`（28,524,560 字节，内部名 `media_trans.exe`）
是一个 **32 位原生 PE**（不是 .NET），版本 1.2.2.0。

PE 头显示三个段：

| 段名 | 虚拟地址 | 虚拟大小 | 文件偏移 | 文件大小 | 特征 |
|---|---|---|---|---|---|
| `UPX0` | `0x00001000` | `0x00735000` | `0x00000400` | `0` | 壳解压目标 |
| `UPX1` | `0x00736000` | `0x004F2000` | `0x00000400` | `0x004F1200` | 壳代码+压缩数据 |
| `.rsrc` | `0x00C28000` | `0x00001000` | `0x004F1600` | `0x00000A00` | 资源 |

`UPX1` 段偏移 `0x3E0` 处有 `UPX!` 标记，前面是版本串 `3.94`，因此确定是
**UPX 3.94** 壳。`UPX1` 的熵为 7.931（接近 8.0），确认是压缩数据。

### 1.2 尾部载荷（关键发现）

段表**完全没有覆盖**文件从 `0x4F2000` 到末尾约 **23 MB** 的区域。
这个区域开头是 `0b 4a bb 03 77 54 00 78 da ...`，其中 **`78 da` 是 zlib 流的标志**。

测量结果：

```
zlib 流起点   0x4F2007
压缩后大小    0x01641FC9 = 23,338,953 字节
解压后大小    0x03775400 = 58,151,936 字节
流结束位置    0x1B33FD0，与文件末尾 0x1B34010 相差 64 字节
```

前 7 字节 `0b 4a bb 03 77 54 00` 是容器头部：

```
偏移  大小  取值        含义
0x00  4    9a0e23ba    魔数
0x04  4    0x12 = 18   文件条目数
0x08  1    0           保留
0x0B  4    0x37754     目录总长度
```

### 1.3 归档目录表

目录表从偏移 `0x20` 开始，每项 **0x210 字节**：

| 项内偏移 | 大小 | 含义 |
|---|---|---|
| `+0x00` | 4 | 标志位 |
| `+0x04` | 4 | 数据偏移 |
| `+0x08` | 4 | 数据长度 |
| `+0x0C` | 4 | 保留（0） |
| `+0x10` | 0x100 | ASCII 文件名（补零） |

18 个条目，数据区全部按 `0x100` 对齐，且**首尾相接无空洞**。

## 3. F1A 格式

### 3.1 头部

4 个独立编码样本的前 19 字节：

```
sil16k.f1a     cb 80 bf f0 06 67 72 aa 66 17 f7 80 00 00 00 00 00 00 00
short16k.f1a   cb 81 bf f0 06 67 72 aa 66 17 f7 9d 9f b6 65 3f 4a 91 10
s16_16k.f1a    cb 81 bf f0 06 67 72 aa 66 17 f7 9d 6f b9 14 4a 22 22 21 1e
ramp16k.f1a    cb 81 bf f0 06 67 72 aa 66 17 f7 9c 8f 5e a8 a8 1b aa 9a 5f
```

`0x00–0x0A` 除第 1 字节外**完全相同**，因此头长确定为 **11 字节**。

### 3.2 帧长 256 采样 [已验证]

所有实测解码长度都是 256 的整数倍：

| 文件 | 文件大小 | 解码样本数 | ÷256 |
|---|---|---|---|
| `short16k.f1a` | 186 | 1024 | 4 |
| `s16_16k.f1a` | 966 | 8192 | 32 |
| `ramp16k.f1a` | 1014 | 8192 | 32 |
| `sil16k.f1a` | 19 | 8704 | 34 |

### 3.3 VBR [已验证]

| 文件 | 大小 | 时长 | 比特率 |
|---|---|---|---|
| `s16_16k.f1a` | 966 | 0.512 s | 15,093.8 bit/s |
| `ramp16k.f1a` | 1014 | 0.512 s | 15,843.8 bit/s |
| `short16k.f1a` | 186 | 0.064 s | 23,250 bit/s |
| `sil16k.f1a` | 19 | 0.544 s | 279.4 bit/s |

目标 16 kbps，实测接近但不等，静音塌缩到 279 bit/s，确定是 VBR。

### 3.4 静音逃逸码 [已验证]

`sil16k.f1a` 共 19 字节：

```
cb 80 bf f0 06 67 72 aa 66 17 f7 | 80 00 00 00 00 00 00 00
<--------- 11 字节头 ----------->  <-- 8 字节载荷 -->
```

载荷只有**一个置位比特**，却解出 **8704 个静音采样**，
证明存在"零游程逃逸"编码。

### 3.5 变异实验 [已验证]

对 `s16_16k.f1a`（基线 966 字节 → 8192 样本）做删除测试：

| 删掉的字节 | 大小 | 解码器输出 | 样本数 |
|---|---|---|---|
| 0 | 966 | 无 | 8192 |
| 1 | 965 | 无 | 9824 |
| 2 | 964 | `overflow in spectral RLE, ignoring` | 5520 |
| 4 | 962 | `overflow in spectral RLE, ignoring` | 14464 |

**删掉恰好 1 字节仍能干净解码**，说明载荷起点在头字节内部、不是字节对齐的。
删 2 字节以上位读取器失步，触发 RLE 溢出告警。

截断测试：截掉最多 64 个尾字节，样本数不变（7936 = 31×256），
说明解码器**只按整帧输出**。

### 3.6 编码器行为 [已验证]

编码器先写临时文件 `tmpf1a.a`，再复制到目标文件并**追加 1 字节**：

```
my16k.f1a   1810 字节
tmpf1a.a    1809 字节
公共前缀    1809 / 1809  → 完全一致
追加字节    0x24
```

### 3.7 未能还原的部分

- **8kHz 的头部编码**：编码器只接受 8000/16000 Hz 的 WMA，
  但 `WMAEncode.exe` 恒定输出 22050 Hz、`ffmpeg` 的 WMA 编码器最低 24000 bps
  （F1A 要求 ≤16000）。两边约束冲突，因此**始终造不出 8kHz 样本**。
- **帧内参数块**（尺度因子、模式位、窗标志）：解析器在约 8KB 的 `.text`
  里内联展开并通过间接跳转分派，未能解析出命名字段。
- **频谱 RLE 码字表**：确认逃逸存在，但码字表未还原。
- **变换参数**：在 `0x404F9x`–`0x4051xx` 找到疑似窗函数/MDCT 系数
  （如 `0x3F7E60C4` ≈ 0.994），在 `0x405760` 找到单调整数表
  `64 00 c8 00 2c 01 90 01 fe 01 76 02 ...`，疑似尺度因子查找表，
  但**未验证**其具体语义。

## 4. `.a` / `.b` / `.e` 格式

### 4.1 `.e` 的魔数 [已验证]

```
ext_8000.e   57 41 56 00 77 7d 77 77 e0 80 7b 7b 80 71 1f 80 ...
ext_16000.e  57 41 56 01 77 7d 77 77 e0 80 7b 7b 80 71 1f 80 ...
             ^^^^^^^^^^^ "WAV" + 采样率码
```

第 4 字节是采样率选择器，实测取值：

| 码 | 采样率 |
|---|---|
| `0x00` | 8000 |
| `0x01` | 16000 |
| `0x02` | 32000 |
| `0x03` | 12000 |
| `0x04` | 24000 |
| `0x77` | 其它（哨兵值） |

**注意**：`.e` 文件**不做重采样**，输出长度只取决于输入帧数。
因此不同采样率的 `.e` 文件，音频数据部分完全相同，差别只在播放速率。

### 4.2 `.a` 的前导 [已验证]

`.a` 没有魔数，前 **44 字节全为零**，第 45 字节起是音频数据。

**该区域可证明为空**：无论输入是静音、直流、正弦、斜坡、满幅噪声、阶跃
还是计数器，前 44 字节都是零；脉冲扫过全部 8000 个位置也从未触碰到它。

另外实测 **`wavtoa.exe` 完全忽略输出扩展名**：`.a`/`.b`/`.e`/`.f1a`/`.raw`/
`.bin`/无扩展名产生的文件**字节完全相同**。所以 `.a` 和 `.b` 本质是同一种
容器，工具包里也找不到独立的 `.b` 编码器。

### 4.3 解码算法 [已验证]

**教科书标准 IMA ADPCM**，没有任何杰理私有变体：

- 4 bit/样本
- **高半字节在前**（`nib0 = byte >> 4`）
- 标准 89 项步长表
- 索引调整表 `[-1,-1,-1,-1,2,4,6,8,-1,-1,-1,-1,2,4,6,8]`，用 **`nibble & 7`** 索引
- 预测器初值 0、步长索引初值 0
- **没有块头、没有周期性重置、没有幅度重缩放**

#### 判定依据一：字节级重编码往返 [最强证据]

ADPCM 是确定性算法，因此"解码官方载荷 → 用同样算法重新编码"
必须**逐字节还原原始载荷**。实测在全部样本上一致度都是 **1.000000**：

| 文件 | 采样数 | MSE | SNR | 重编码一致度 |
|---|---|---|---|---|
| `zz_counter.a` | 7766 | 200,955.80 | 26.03 dB | **1.000000** |
| `v_ramp.a` | 7766 | 956,200.78 | 25.49 dB | **1.000000** |
| `v_sine440.a` | 7766 | 352,819.05 | 27.53 dB | **1.000000** |
| `v_noise.a` | 7766 | 8,683,148.50 | 16.11 dB | **1.000000** |
| `v_step.a` | 7766 | 2,057,409.38 | 22.89 dB | **1.000000** |
| `cmp8.e` | 8022 | 1,149,734.26 | 22.40 dB | **1.000000** |
| `ee_16000.e` | 16022 | 570,689.45 | 25.45 dB | **1.000000** |
| `ee_12000.e` | 12022 | 802,608.46 | 23.97 dB | **1.000000** |

字节级往返一致**同时**验证了半字节顺序、步长表、索引表、初始状态四个要素，
比任何相关性指标都强。残余 MSE 就是 4bit ADPCM 的量化噪声本身。

#### 判定依据二：脉冲扫描确定预热偏移 [已验证]

把单个脉冲扫过全部 8000 个输入位置，记录载荷中第一个变化的字节：

| 脉冲位置 k | 首个差异字节 | 模型预测 `(k-236)//2+1` |
|---|---|---|
| 234 | 0 | 0 ✓ |
| 236 | 1 | 1 ✓ |
| 250 | 8 | 8 ✓ |
| 500 | 133 | 133 ✓ |
| 1000 | 383 | 383 ✓ |
| 2000 | 883 | 883 ✓ |
| 4000 | 1883 | 1883 ✓ |

从 k=236 到 k=4000 **零跳变**。这同时证明了两件事：

1. **编码器丢弃前 234 个输入样本**（预热），解码样本 i 对应输入样本 `i + 234`。
2. **完全不存在按块重置** —— 如果有块结构，每个块边界都会产生跳变，
   而实测在 128/256/512/1024/2048 各种块大小的边界处误差**精确为 0.00**。

`.e` 则多编码 256 个 nibble 的预热，即解码样本 i 对应输入样本 `i - 22`。

长度公式（实测 21 个点验证）：

```
len(.a) = 44 + ceil((n-235)/2)
len(.e) = 4 + ceil((n+21)/2)
```

#### 一个被推翻的假设

早期用"搜索最佳 `(头部偏移, 初始预测器, 滞后)` 三元组"的方式拟合，
得到 `hdr=84, pred0=-16000`，看似完美（MSE 0）。
但这其实是**拟合退化**：三个参数互相补偿，很多组合都能得到 MSE 0。
`-16000`（`C1 80`）在任何文件里都不存在，因为**它从来不被存储**。
正确模型是简单的 `hdr=44, pred=0, idx=0` 加上 234 样本的偏移。
教训是：**多参数拟合的"完美结果"必须用独立方法交叉验证**。

### 4.4 工具命令行

```bash
wavtoa.exe   <input.wav> <output.a>          # 只接受 8000 Hz
e_wavtoa.exe <input.wav> <output.ext> <rate> # rate ∈ {12000,16000,24000,32000}
```

`wavtoa.exe` 对非 8000 Hz 输入会报 `Samples != 8000!!` 并拒绝，写入 0 字节。

**重要**：这些工具**必须用绝对路径调用**。用相对路径或不带参数调用会以
`0xC0000417`（fail-fast）崩溃；带绝对路径时一切正常。

**`raw2rawbig.exe`** 的行为也已还原：

```
raw2rawbig.exe <in.raw> <out.raw>
输出大小 = 输入大小 + 8192
布局: [0..8191] 是 8 KiB 前导（输入数据在其中平铺出现）
      [8192..8192+k) = in[0:k], k = min(len, 4096)
      之后是输入的剩余部分
```

尽管名字叫 "rawbig"（暗示大端），实测**没有任何字节交换**：
输入 `01 02 03 04` 输出仍是 `01 02 03 04`。
1 个参数 = 无操作（返回 0），0 个参数 = 崩溃，第 3 个参数被忽略。

## 5. `.ump3` 格式

### 5.1 结论：就是 MP3 [已验证]

**决定性证据** —— 同一个源、同一个编码器、同一组参数，
分别输出成两个扩展名：

```
smp_16k_64k.ump3  size=8973  sha256=07c338a1f8eb2cedb3f945b59902127d0d687cbc...
ctl_16k_64k.mp3   size=8973  sha256=07c338a1f8eb2cedb3f945b59902127d0d687cbc...
byte-identical: True
```

十六进制也完全吻合：

```
49 44 33 04 00 00 00 00 00 23   ID3v2.4 标签，45 字节
54 53 53 45 00 00 00 0f 00 00 03 4c 61 76 66 35 37 2e 31 34 2e 31 30 30
                                TSSE = "Lavf57.14.100"
FF F3 88 C0                     MP3 帧同步（MPEG-2 L3, 64kbps, 16kHz, 单声道）
```

MP3 帧遍历器在 MPEG-1 / 2 / 2.5 以及 8k / 16k / 44.1k 全部样本上
做到**零错位、零残留字节**。

### 5.2 杰理对 FFmpeg 的修改：无 [已验证]

`ump3_ffmpeg.exe`（35,250,176 字节）是**上游原版 FFmpeg N-76648-g6f520ce（2015）**：

- 341 处 `/home/kyle/software/ffmpeg/source/ffmpeg-git` —— 标准的上游 win32 静态构建路径
- `ump3` / `UMP3` / `jieli` / `JieLi` / `zhuhai` / `br20` **零命中**
- `-h muxer=ump3` 报 `Unknown format 'ump3'`

少数 `jie` / `f1a` / `f1c` 命中经逐条核对都在原始二进制字节和
OpenCL 着色器源码（`int2 fref1Apos`）里，是巧合。

**也就是说 "UMP3" 只是 GUI 运行时拼出来的文件扩展名。**

### 5.3 转换命令

```bash
ump3_ffmpeg.exe -y -i input.ump3 output.wav
```

不需要剥头、不需要跳偏移、不需要额外参数。

## 6. 工具实现

### 6.1 分层

```
jie2wav.py        命令行入口：参数解析、批量、输出命名去重
    ├── common.py    WAV 读写、格式嗅探、hexdump
    ├── f1a.py       容器解析与校验（纯 Python）
    │   └── f1a_decoder.py   解码后端（调用随包官方解码器）
    ├── abe.py       .a/.b/.e 纯 Python IMA ADPCM 解码
    └── ump3.py      MP3 结构解析（纯 Python）+ 解码（FFmpeg）
```

### 6.2 为什么 F1A 用官方解码器

F1A 的帧内结构没有完全还原（见 3.7），所以解码这一层委托给
随包分发的 `tools/testf1a_dec.exe`。这样做的好处是输出与官方工具
**逐字节相同**（已用 SHA-256 验证），代价是这一个环节依赖该二进制。

容器解析、格式校验、输出规范化、批量处理、命名去重全部是本工具自己的逻辑。

### 6.3 输出命名去重

同名不同扩展名的输入（`voice.a` / `voice.b` / `voice.e`）会输出到
`voice.wav` 而互相覆盖，因此当检测到同名组时自动追加扩展名：
`voice_a.wav` / `voice_b.wav` / `voice_e.wav`。

### 6.4 自检

`wav_tool/selftest.py` 覆盖 6 组共 21 项检查，当前全部通过：

```
[1] F1A 容器解析（同步字节、指纹、载荷偏移、损坏拒绝）
[2] F1A 解码对比官方（逐字节一致）
[3] A/B/E 容器解析（前导、魔数、采样率字节）
[4] A/B/E 解码保真度（相关性 1.00000 / 0.99988）
[5] UMP3 = MP3（哈希一致 + MP3 结构解析）
[6] 端到端 CLI（4 个格式全部转换成功）
```

## 7. 未能确定的问题

诚实列出：

1. **8kHz F1A 的头部编码方式**。工具链约束冲突导致造不出样本，
   所有可生成文件的头字节除第 1 字节外完全相同，采样率字段无法分离。
2. **F1A 帧内参数块**（尺度因子、模式位、窗标志）的具体字段宽度。
3. **F1A 频谱 RLE 的码字表**。确认逃逸存在及其行为，但码字表未还原。
4. **F1A 变换类型与参数**。找到疑似窗/MDCT 系数表和尺度因子表，未验证。
5. **F1A 尾部 1–2 字节**（`0xC0`/`0xC8` 重复对）的语义。
   已确认编码器追加 1 字节，但无法证明它是终止符、刷新计数还是校验。
   **全文件未发现任何校验和字段**。
6. **`.a` 44 字节前导的用途**。可证明其内容为空（任何输入都是全零），
   但芯片端为何保留这段空白不得而知。
7. **编码器合成预热波形的具体形状**。只确定其**长度**（`.a` 为 234 个样本的
   丢弃、`.e` 为 -22 的预卷），波形本身未被观测。
8. **`cutmp3_energy.exe` 的精确能量公式**。裁剪行为已确认
   （1 秒音 + 1 秒静音，阈值 ≥10 时从 59 帧裁到 29 帧），
   但打印的两个数字的确切含义未定。
9. **`tail.bin`（64 字节，以 `JL_ZIP` 结尾）的用途**。
10. **`add_f1a_head.exe` 的接口**。本机缺少 VC++2015+ 的 UCRT API-set DLL
    （`api-ms-win-crt-*-l1-1-0.dll`），所有调用在打印前就以 `0xC0000142` 退出。
    这是环境限制，不是分析结论。
11. **`wavtoa.exe` 为何坚持要求恰好 8000 帧**。
12. **`.b` 是否有独立的编码器**。工具包里没有找到，
    且 `wavtoa.exe` 忽略扩展名，因此推测 `.b` 只是命名约定。
