# 杰理音频转 WAV 工具

把杰理（JieLi）AD14N / SH50 系列的音频文件转回标准 WAV。

---

## 快速开始

**图形界面**：双击 `启动转换工具.bat`

**命令行**：

```bash
python wav_tool/jie2wav.py 文件.f1a                   # 单个文件
python wav_tool/jie2wav.py *.f1a *.a *.ump3 -o out    # 批量
python wav_tool/jie2wav.py --info 文件.f1a            # 只看格式信息
python wav_tool/jie2wav.py 音乐.f1a -r 16000          # 手动指定采样率
```

## 支持的格式

| 扩展名 | 格式实质 | 采样率 | 实现方式 |
|---|---|---|---|
| `.f1a` `.f1b` `.f1c` | 杰理私有频谱编码 | 8000 / 16000 | 随包官方解码器 |
| `.a` `.b` | IMA ADPCM 4bit | 8000 | 纯 Python |
| `.e` | IMA ADPCM 4bit | 8000–32000 | 纯 Python |
| `.ump3` | **标准 MP3** | 任意 | 随包 FFmpeg |

---

## 三种格式的真相

### `.ump3` 就是 MP3

没有任何私有封装。同一个源、同一个编码器、同一组参数，分别存成
`.ump3` 和 `.mp3`，两个文件 **SHA-256 完全相同**：

```
smp_16k_64k.ump3  sha256 = 07c338a1f8eb2cedb3f945b59902127d...
ctl_16k_64k.mp3   sha256 = 07c338a1f8eb2cedb3f945b59902127d...
```

文件开头是标准的 `ID3` 标签 + `FF F3` MP3 帧同步。
所谓的 "UMP3" 只是 GUI 里用的**文件名后缀**而已。

### `.a` / `.b` / `.e` 是标准 IMA ADPCM

也是通用算法，不是私有的：

- 4 bit/样本
- **高半字节在前**
- 标准 89 项步长表 + `[-1,-1,-1,-1,2,4,6,8,...]` 索引调整表（用 `nibble & 7` 索引）
- 预测器初值 0、步长索引初值 0
- **没有块头、没有周期性重置、没有幅度重缩放**

**证明方式（最强的一种）**：ADPCM 是确定性算法，所以把官方产生的载荷
解码后用同样的编码器再编码，必须**逐字节还原原文件**。实测在全部样本上
一致度都是 **1.000000**：

```
amp_0.a       re-encode byte-identical (1.000000, 3883 bytes)
amp_1.a       re-encode byte-identical (1.000000, 3883 bytes)
zz_counter.a  re-encode byte-identical (1.000000, 3883 bytes)
...
```

字节级往返一致**同时锁定**了半字节顺序、两张表、初始状态。

#### 容器的区别

| 容器 | 头部 | 解码样本 i 对应输入样本 |
|---|---|---|
| `.a` | 44 字节全零 | `i + 234`（前 234 个样本不存在）|
| `.b` | 同 `.a`（扩展名被忽略）| `i + 234` |
| `.e` | `57 41 56 xx`（"WAV"+采样率码）| `i - 22`（多 22 个预卷样本）|

`.e` 的采样率码：`0x00`=8000、`0x01`=16000、`0x02`=32000、
`0x03`=12000、`0x04`=24000，其它采样率用 `0x77` 哨兵值。

工具默认会**对齐到原始起点**（丢掉 `.e` 的预卷），
加 `--raw-delay` 可以保留原始采样。

### `.f1a` 是真正的私有编码器

只有这个是真的私有格式，包含 MDCT 类变换 + 尺度因子 + 频谱游程编码 + 位流打包。

**容器结构已完全还原**：

| 偏移 | 大小 | 取值 | 含义 |
|---|---|---|---|
| `0x00` | 1 | `0xCB` | 同步字节 |
| `0x01` | 1 | `0x80` / `0x81` | 模式标志（bit0 = 含真实音频）|
| `0x02` | 9 | `BF F0 06 67 72 AA 66 17 F7` | 固定编解码器指纹 |
| `0x0B` | .. | — | MSB 优先编码比特流 |

- **每帧 256 采样**，解码结果都是 256 的整数倍
- **是 VBR**：目标 16 kbps，实测 0.28–23 kbit/s，完全跟内容走
- **没有长度字段、没有帧数、没有校验和**，解码器从**文件大小**推算时长
- **静音塌缩极厉害**：`sil16k.f1a` 只有 19 字节却解出 8704 个静音采样

**帧内参数和 RLE 码字表未能还原**，所以解码调用随包分发的官方解码器
`tools/testf1a_dec.exe`。

---

## ⚠️ 关于 F1A 的采样率（重要）

**F1A 文件里没有可靠的采样率字段。**

- 头部第 1 字节以外，所有能生成的样本完全相同，采样率字段无法分离
- 官方解码器更麻烦：它**固定把 16000 写进 WAV 头**，与真实流无关
- 对无头文件它还会写错字节率字段（写成采样率而不是采样率×2）

所以工具默认按 **8000 Hz** 处理，这是实测校验过的值：

| 判据 | 结果 |
|---|---|
| 听感 | 8000 Hz 下音调正常 |
| 节奏自相关 | **130.4 BPM**，正好落在 Funk 典型区间 125–135 |
| 隐含码率 | 7,943 bit/s，符合 8 kHz 低码率音乐 |

**如果音调不对，请在界面里手动选择其它采样率**，或在命令行加 `-r 16000`。

## 无头 F1A 文件

有些 F1A 文件**没有那 11 字节头**，直接就是编码载荷（工具包里
`add_f1a_head.exe` 就是用来给它们补头给芯片用的）。

本工具能自动识别这类文件并正确解码 —— **不需要补头**。
补头反而会让时长翻倍，因为解码器是按文件大小算时长的。

## 已知限制

1. **F1A 帧内结构未完全还原**，解码依赖随包官方解码器。
   容器解析、校验、输出规范化都是本工具自己的逻辑。
2. **F1A 采样率需要人工判断**（原因见上）。
3. **`.a` 的 44 字节前导始终是全零**，没有观察到有效字段。
4. **只做解码，不做编码**。生成这些容器是官方软件的职责，
   尤其是 `.f1a` 的私有频谱编码器只有官方工具知道。
5. **`.ump3` 需要 ffmpeg**。工具会优先用系统 PATH 里的，
   找不到就用自带的 `tools/ump3_ffmpeg.exe`。
